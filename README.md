# Prediction Market DAO — MVP

Polymarket / みらいマーケット的な、労働（広告視聴・アンケート）で貯まるコミュニティ金庫（Treasury）を原資に、サッカーの試合結果からYes/No質問・複数選択肢の問いまで自由に予測できるパリミュチュエル方式のWebアプリのMVP。

設計ドキュメント一式は [`docs/`](./docs) を参照してください（DBスキーマ解説・バックエンドロジック解説・ワイヤーフレーム）。

## 技術スタック

- Next.js (App Router) / TypeScript / Tailwind CSS
- Postgres（Supabase向けに書かれたスキーマ・RPC関数一式を、ローカルではSupabaseプロジェクトの代わりに素のPostgresへ直接適用して動かしています。同じマイグレーション一式がSupabaseにもそのまま適用できます — ローカル専用の`00000000000000_local_dev_auth_shim.sql`はSupabaseを検出すると自動的に何もしないため、除外する操作は不要です）

## セットアップ（ローカル開発）

前提: Node.js 20+、ローカルにPostgres 16が起動していること。

```bash
# 1. 依存関係のインストール
npm install

# 2. DBを作成
createdb prediction_market

# 3. 環境変数を用意（デフォルトのままでOK。スポーツAPI連携はキーなしのモックプロバイダで動きます）
cp .env.example .env.local

# 4. マイグレーションを適用（未適用のものだけが実行されます）
npm run migrate

# 5. デモ用データを投入（管理者アカウント・タスク・マーケットのseed）
npm run seed
npm run seed-news   # News-Firstフィード(/news)検証用のデモ記事＋紐付けマーケット（任意）

# 6. 開発サーバーを起動
npm run dev
```

http://localhost:3000 を開くとアプリが動きます。

## 実装済み機能

- 認証（サインアップ / ログイン / セッションCookie）。新規登録時に金庫から**1000ptのウェルカムボーナス**（`SIGNUP_BONUS_POINTS`）
- **マーケットメイカー経済圏**: ユーザーがマーケットを即公開でき（作成料`MARKET_CREATION_COST`は**現在0＝無料**。本来は100ptのスパム対策の関門で、人が集まったら戻す前提）、そのマーケットが精算されると手数料の10%（`MARKET_CREATOR_FEE_BPS`）が作成者の報酬になります。盛り上がるほど作成者の取り分が増えるので、人気の出るお題を作るインセンティブが働きます。無料の「提案＋賛成投票」経路も残していますが、そちらに作成者報酬はありません（後述）
- タスクセンター: 広告視聴（デモ版はシミュレーション再生）・アンケート回答 → `complete_task` RPCで自動ポイント付与＆金庫更新
- **マイクロワーク市場（スポンサー案件）**: 広告主・代理店・業務委託の発注者から運営が円で対価を受け取り、その原資でユーザーにポイントを付与する仕組み。案件ごとの受取額・予算上限・採算（逆ざやの検出）を管理し、人の作った成果物はユーザー同士の相互チェックか運営検収を通してから支払われます（後述）
- マーケット一覧・詳細・パリミュチュエル方式のベット（`place_bet` RPC）。**的中者には賭けた分が必ず全額戻り**、そのうえで他の選択肢のプールから運営手数料を除いた分を山分けします。他の選択肢に誰もベットしていなければ手数料もかからず、賭けた分がそのまま戻ります（後述）
- **ベットの取り消し**（`cancel_bet` RPC）: 締切前なら3pt（`BET_CANCEL_PENALTY`）のペナルティを引いて返金されます。また**同じマーケットで別の選択肢に賭けることはできません**（両建てで確実に取り分を得る抜け道を塞ぐため）
- **関連マーケットの表示**: ベット画面の下部に、同じニュース → 同じリーグの同節 → 同じリーグ → 同じカテゴリ、の優先順で関連するオープン中のマーケットを表示します
- **お題の形式は自由**: 試合の勝敗（ホーム/引分/アウェイ）だけでなく、Yes/No質問（例:「開幕戦で〇〇選手はスタメン出場するか？」）や、2〜8個の任意の選択肢を持つマーケットも作成できます（`markets.market_kind` + `outcome_options`）
- お題提案 → 賛成票が閾値（既定3票、`MARKET_APPROVAL_THRESHOLD`で変更可）に達すると自動オープン
- **コミュニティ判定（保証金付きOptimistic Oracle）**: 結果の判定は**誰でも提案できます**。提案後24時間（`DISPUTE_WINDOW_MINUTES`）以内に異議が出なければ自動確定・精算、異議が出ればDAO投票の多数決で最終決定します（`finalize_expired_markets` RPCが`sync_market_status`と同様にマーケット閲覧のたびに遅延実行される簡易cron）。詳細は後述
- **早期確定（締切前の判定）**: 結果がキックオフ前に判明した場合、100pt（`EARLY_RESOLUTION_BOND`）を預けてベットを即座に停止し、3時間（`EARLY_RESOLUTION_VOTING_HOURS`）のDAO投票にかけられます（後述）
- **結果報告の報酬と罰則**: 結果の報告には保証金100pt（`RESOLUTION_BOND`）が必要で、その報告が確定すれば**保証金の返却＋100pt**（`RESOLUTION_REWARD`）、DAO投票で覆されれば没収されます。証跡URLは**任意**です（後述）
- **結果入力のタスク化**: 結果判定の予定日時（作成時に必須）を過ぎてもまだ報告がないマーケットは、`/tasks`に「結果の入力」として掲示されます
- **管理者によるマーケット作成**: 管理者は作成料なしでマーケットを公開できます。初期賞金は金庫が負担し、代わりに作成者報酬は受け取りません（後述）
- **通報によるマーケットの停止**: ガイドライン違反のマーケットは誰でも通報でき、3件（`MARKET_BAN_THRESHOLD`）で即座に停止・全額返金されます。作成料は没収され、通報者には30pt（`REPORT_REWARD`）。禁止されている主題は作成時点で自動拒否されます（後述）
- **判定投票の報酬**: 正解の選択肢へ投票した人のうち先着10名（`VOTE_REWARD_SLOTS`）に30pt（`VOTE_FLAT_REWARD`）、さらに正解者全員で手数料の50%（`VOTER_RAKE_SHARE_BPS`）を按分。10票集まるまでは`/tasks`に「タスク」として表示されます
- 管理者による緊急オーバーライド（オラクルをスキップした即時確定・全額返金での中止）
- **RSSニュース取り込み**（`scripts/sync-news.mjs`）: Yahoo!ニュース・NHKなどのRSSから記事を取り込み、`/news`フィードに表示。常駐更新（`--watch`）と画面上の更新ボタン／APIエンドポイントに対応（後述）
- **試合マーケットの自動生成**（`scripts/sync-fixtures.mjs`）: 近日中の試合をTheSportsDBの無料APIから取得し、初期賞金つきのマーケットを自動作成します。日次Cron・管理画面のボタン・CLIのいずれからも実行でき、`external_ref`で冪等なので重複しません（後述）
- マイページ（ベット履歴・ポイント履歴）
- 金庫（Treasury）ダッシュボード（公開・収益源の内訳）

### 初期賞金（シード）— 最初のベットに意味を持たせる仕組み

stake-back保証があるため、誰もベットしていないマーケットに賭けても「損はしないが得もしない」状態になり、最初にベットする動機がありませんでした。

そこで**作成料のうち90%（`MARKET_SEED_BPS`）を「初期賞金」としてマーケットに積む**ようにしています。作成料100ptなら90ptが賞金です。

> **現在は作成料が0なので、ユーザーが作るマーケットに初期賞金は付きません。** stake-back保証があるため賭けた人が損をすることはありませんが、反対側に誰もいないマーケットは増減なしで終わります。自動生成マーケットと管理者作成マーケットには、金庫が負担する初期賞金（`AUTO_MARKET_SEED` / `ADMIN_MARKET_SEED`）が付きます。この賞金は精算時に的中者へ上乗せ分配されるため、反対側に誰もいなくても勝てばポイントが増えます（100pt賭けて的中なら190pt）。残り10ptが運営手数料です。

金庫は作成時に100ptを預かり、精算時に90ptを的中者へ払い出す「預かり役」になります（`market_seed_payout`として台帳に記録）。マーケットが中止された場合は作成料が全額返金され、賞金は払い出されません。

### パリミュチュエル配当の仕組み（stake-back保証）

他の選択肢に誰も賭けていない場合でも的中者が損をしないよう、手数料は「他の選択肢（外れた側）のプール」からのみ徴収します。

- 総プール = 的中した選択肢のプール + 他の選択肢のプール合計
- 手数料 = 他の選択肢のプール合計 × 手数料率（既定10%）
- 的中者への配当 = 自分の賭け金（全額） + 自分の賭け金 ÷ 的中した選択肢のプール × (他の選択肢のプール合計 − 手数料)

他の選択肢のプールが0（誰も逆張りしていない）なら、手数料も0になり、賭けた分がそのまま戻ります。

### マーケットの作り方（3つの経路）

| | 通常（現在は無料） | 提案 | 管理者 |
|---|---|---|---|
| コスト | **0pt**（本来は100pt） | 0pt | 0pt |
| 公開まで | **即時** | 賛成3票が集まるまで | **即時** |
| 初期賞金 | **なし**（作成料から出るため） | なし | 90pt（**金庫が負担**、`ADMIN_MARKET_SEED`） |
| 作成者報酬 | 手数料の**10%** | なし | なし |
| 入口 | `/news` の各記事、または `/markets/propose` | `/markets/propose` | `/admin` |

**作成料が0の間、作成画面のタブは出ません。** 「即時公開＋手数料の分け前あり」が「賛成票を待つ＋報酬なし」に対して一方的に有利で、選ばせる意味がないためです。作成料を戻せばタブも戻ります。

有料経路では、精算時の手数料（外れた側のプールの10%）がさらに分割され、その10%が作成者に、残り90%が金庫に入ります。マーケットが中止（void）になった場合は、作成者に非がないため作成料100ptは返金されます。

管理者経路は「板が寂しいときに運営が場を用意する」ためのものです。作成料を払わない代わりに初期賞金は金庫が出し、**作成者報酬は受け取りません**（運営が場を用意しつつ手数料も抜く、という形にならないようにしています）。金庫の残高が初期賞金に足りない場合は`insufficient_treasury`で拒否されます。

### マーケットの形式（お題の種類）

3種類のお題を作成できます。

| market_kind | 内容 | outcome_options の例 |
|---|---|---|
| `match_winner` | 試合の勝敗（3択） | ホーム/引分/アウェイをチーム名から自動生成 |
| `binary` | Yes/No質問 | `[{"key":"yes","label":"はい"},{"key":"no","label":"いいえ"}]` |
| `multi_outcome` | 自由な複数選択肢（2〜8個） | 提案者が入力したラベルから生成（`key`は`opt1, opt2, ...`） |

ベット・配当計算・Optimistic Oracle・DAO投票はすべて`outcome_options`ベースの汎用ロジックで動作するため、選択肢の数や種類に関わらず同じ仕組みで扱えます。

作成時には以下も指定できます。

- **カテゴリ**（サッカー / 野球 / 経済 / 金融・為替 / 政治 / テック / エンタメ など）— 一覧のフィルタとアイコンに反映されます
- **結果判定の予定日時（必須）** — ベット締切とは別の「いつ結果が分かるか」です。この時刻を過ぎると`/tasks`に結果入力タスクとして掲示されます
- **大会・リーグ／第何節**（スポーツカテゴリのみ）— 後述の検索で使います

### スポーツの試合マーケットを探しやすくする

自動生成されたものもユーザーが手で作ったものも、同じ試合が重複したり探せなくなると困るので、**大会・リーグと第何節を構造化データとして持たせて検索できる**ようにしています。

- `/markets` にキーワード検索（チーム名・リーグ名・タイトル・説明を対象）
- カテゴリ、リーグ、第◯節での絞り込み（実在するものだけがチップとして出ます）
- マーケット詳細のカテゴリ/リーグ/節タグからも同じ絞り込みに飛べます

日本語のためPostgresの全文検索（tsvector）ではなくILIKEによる部分一致にしています。件数が増えた場合は`pg_trgm`+GINインデックスへの移行が適切です。

### 結果の判定 — コミュニティ判定（保証金付きOptimistic Oracle）

**なぜ人力なのか**: 当初はスポーツAPIで自動判定する想定でしたが、API-Footballの無料プランは現行シーズンにアクセスできませんでした（`"Free plans do not have access to this season, try from 2022 to 2024."`）。そもそもユーザーが作る任意のお題（「〇〇選手はスタメンで出るか」など）はどのAPIでも判定できません。そこで判定を人に戻し、Optimistic Oracleで担保する設計にしています。

```
ベット締切（キックオフ通過で自動ロック）
   ↓
結果判定の予定日時を通過 → /tasks に「結果の入力」として掲示
   ↓  誰でも報告できる（保証金 100pt、証跡URLは任意）
報告中（pending_resolution）← ここで賭けた人に「暫定 的中/不的中」が見えます
   ↓  24時間以内に異議なし          ↓ 異議あり
自動で確定・精算                    DAO投票の多数決で決定
保証金の返却 ＋ 報酬 100pt           報告が支持されれば返却＋100pt / 覆されれば没収
```

保証金（`RESOLUTION_BOND`）は、**自分のベットに有利な結果を報告して誰も気付かないのを狙う**攻撃を防ぐためのものです。嘘をつく利益より没収額が大きければ割に合わなくなるので、運用に合わせて調整してください。

#### 結果を入力する動機（報酬 10pt）と、間違えたときの罰則

保証金が返ってくるだけでは、報告する理由になりません（何もしなくても手持ちは減らないため）。そこで**報告が確定したら保証金の返却に加えて100pt**（`RESOLUTION_REWARD`）を支払います。当初は10ptにしていましたが、保証金100ptを預けて報告する割に合わず、報告が集まりませんでした。

| 報告の結末 | 報告者の収支 |
|---|---|
| 異議なしで確定 | 保証金100pt返却 ＋ **報酬10pt** |
| 異議が出たがDAO投票で支持された | 保証金100pt返却 ＋ **報酬10pt** ＋ 異議側の没収分70pt |
| DAO投票で覆された | 保証金100pt **没収**（うち70ptが異議申立者へ） |

報酬の原資は、マーケット作成時に金庫が受け取る100ptのうち初期賞金にならなかった10ptです。**そのマーケットが「自分を判定してもらうために取り分けた金」がそのまま判定者に渡る**形になっています。

#### 結果判定の予定日時と「結果の入力」タスク

マーケット作成時に**結果判定の予定日時が必須**になりました（`resolves_at`）。ベット締切とは別に、「いつ答えが分かるはずか」を宣言してもらう項目です。

この時刻を過ぎてもまだ結果が報告されていないマーケットは、`/tasks`に**「📝 結果の入力」**として、広告視聴・アンケートと並んで掲示されます。締切後に誰にも気づかれず放置される、という状態をなくすためです。

#### 証跡URL（任意）

結果の報告に証跡URLは**必須ではありません**。以前は必須にしていましたが、「結果は分かっているのに、貼れるURLを探すのが面倒で報告しない」を大量に生んでいました。報告されないマーケットは精算されず、賭けたポイントも戻らないので、誰の得にもなりません。

出典が争点になるのは異議が出たときなので、そこで貼れれば足ります。入力した場合はマーケット詳細に「🔗 証跡を確認する」として表示され、確定後も「🔗 判定の証跡」として残ります。あるほうが他の人は確かめやすく、異議も出にくくなります。

URLを入れた場合の形式チェック（`http(s)://` で始まること）は残しています。証跡欄にリンクとして開けないものが並ぶのを防ぐためです。

#### 締切前に結果が判明した場合（早期確定）

「試合前に出場停止が発表された」「開催そのものが中止になった」のように、キックオフを待たずに答えが確定することがあります。締切まで放置すると、結果を知っている人だけが賭けられる時間ができてしまうため、**誰でも100pt（`EARLY_RESOLUTION_BOND`）を預けて即座にベットを止め、判定にかけられる**ようにしました。

```
オープン中（まだベット可能）
   ↓  「早期確定を申請」（保証金 100pt を預託）
ベット即停止（disputed / resolution_source = community_early）
   ↓  3時間のDAO投票（EARLY_RESOLUTION_VOTING_HOURS）
多数決で確定・精算
申請が支持されれば保証金は返却、覆されれば没収
```

投票の締切が来ると、マーケット閲覧時の遅延cron（`finalize_expired_markets`）が多数決を集計して精算まで進めます。票が1票も入らなかった場合は申請どおりに確定し、保証金は返却されます。

#### 保証金の没収と分配

異議申し立て（通常の異議・早期確定への反対のいずれも）にも**同額の保証金（`CHALLENGE_BOND`）が必要**です。無料だと精算の引き延ばしがタダになってしまうためで、これによって「提案者 vs 異議申立者」が同じ額を賭けて争う形になります。

DAO投票で負けた側の保証金100ptは没収され、**その70%（`BOND_AWARD_BPS`）が勝った側へ、残り30%が金庫**に入ります。

| 結果 | 提案者 | 異議申立者 |
|---|---|---|
| 提案が支持された | 保証金100pt返却 ＋ 70pt獲得 | 保証金100pt没収 |
| 提案が覆された | 保証金100pt没収 | 保証金100pt返却 ＋ 70pt獲得 |

#### 判定投票の報酬

判定を人に任せる以上、「投票する理由」が必要です。そこで**正解の選択肢に投票した人**に2種類の報酬を出します。

- **先着ボーナス**: 正解に投票した人のうち先着10名（`VOTE_REWARD_SLOTS`）に30pt（`VOTE_FLAT_REWARD`）ずつ
- **手数料の按分**: 正解に投票した人**全員**で、そのマーケットの手数料の50%（`VOTER_RAKE_SHARE_BPS`）を頭割り

精算時の手数料は、作成者報酬（10%）→ 投票者への按分（50%）→ 残りが金庫、の順に分割されます。

投票がまだ足りないマーケットは`/tasks`に「結果確定の投票」として広告視聴・アンケートと並んで表示されます。**先着枠は「正解者のうち10名」ですが、投票中は誰が正解かは分からない**ため、タスクとしての掲載条件は「総投票数が10票未満」にしています。

### RSSニュース取り込み

- 取り込んだ記事は`/news`に表示され、ユーザーがそこからマーケットを作成できます。

| 方法 | 使いどころ |
|---|---|
| `npm run sync-news -- --watch` | ローカル開発。既定間隔は`NEWS_SYNC_INTERVAL_MINUTES`（30分）。前回の取り込みが終わってから次の待機に入るので、遅いフィードでも多重実行になりません |

| `POST /api/news/sync` | 外部スケジューラ（cron / GitHub Actions / Vercel Cron等）から叩く。セッションの代わりに`x-news-sync-secret`ヘッダで`NEWS_SYNC_SECRET`を渡します（未設定なら管理者セッションのみ） |

> このセッションの開発環境は外部への通信が遮断されているため、**実際のYahoo!/NHKのフィードに対する接続確認はできていません**。パーサ・取り込み・冪等性・フィード失敗時の挙動は、ローカルに立てたHTTPサーバ経由のサンプルフィード（RSS/RDF/Atom各形式）で検証済みです。

### 近日中の試合からマーケットを自動生成する

「スポーツナビのような一覧から、近日中の試合のマーケットを自動で作る」機能です。

**スクレイピングは採用していません。** Yahoo!スポーツナビをはじめ主要なスポーツ日程サイトは、利用規約で自動収集を禁止しており、日程もJavaScriptで描画されるためHTMLには何も入っていません。仮に動いても、先方がマークアップを変えた時点で壊れます。代わりに**公開APIを使います**。

推奨は [TheSportsDB](https://www.thesportsdb.com/) です。ドキュメント付きの無料APIで、無料のスポーツAPIとしては珍しく**日本のリーグ（J1/J2/J3・NPB・Bリーグなど）を収録**しているのが採用理由です。

**APIキーの設定は不要です。** TheSportsDBは共有の無料キーを公開しており、それを自動で使います。Premiumキーをお持ちの場合のみ`SPORTSDB_KEY`を設定してください。

```bash
# 1. リーグIDを調べる（IDは推測できず、変更されることもあるので必ずここで確認してください）
npm run sports-leagues -- Japan Soccer
npm run sports-leagues -- Japan Baseball

# 結果が0件のときは、APIが何を返したかをそのまま表示できます
npm run sports-leagues -- Japan Soccer --raw
```

確認できたIDの例（2026年8月時点）:

| id | リーグ | category |
|---|---|---|
| 4633 | Japanese J1 League（J1リーグ） | `soccer` |
| 4824 | Japanese J2 League | `soccer` |
| 4967 | Japanese J3 League | `soccer` |
| 5637 | Japan Emperors Cup（天皇杯） | `soccer` |
| 5826 | Japan Football League（JFL） | `soccer` |
| 4591 | Nippon Baseball League（NPB） | `baseball` |

```bash
# 2. .env.local に設定（J1リーグ＋天皇杯の例）
#   SPORTS_API_PROVIDER=thesportsdb
#   SPORTSDB_LEAGUES=[{"id":"4633","name":"J1リーグ","category":"soccer"},{"id":"5637","name":"天皇杯","category":"soccer"}]

# 3. 取り込む
npm run sync-fixtures
```

> `SPORTSDB_LEAGUES`の値は**クォートで囲まないでください**。`[`で始まる1行としてそのまま書きます。`name`は画面表示用なので日本語に書き換えて構いません。

複数リーグを同時に扱えます。`category`は`lib/categories.ts`のキー（`soccer` / `baseball` / `sports_other` など）で、一覧のアイコンと絞り込みに反映されます。

- **1週間分がまとめて作られます**: 取得対象は`SPORTS_API_SYNC_DAYS`日以内（既定14日）にキックオフする試合すべてで、J1と天皇杯を設定していれば1回で数十件になります
- **重複しません**: `external_ref`で冪等なので、毎日実行しても同じ試合が二重に作られることはありません。すでに締切済み・精算済みのマーケットは、元データの日時が後から変わっても更新されません
- **1回あたりの上限は60件**（`SPORTS_API_MAX_MARKETS_PER_SYNC`）。超えた分はキックオフの遅いものから見送られ、次回の同期で取り込まれます
- **初期賞金が付きます**: 自動生成されたマーケットにも金庫が90pt（`AUTO_MARKET_SEED`）の賞金を積みます。これがないと最初にベットする人が損も得もしない状態になり、自動で並べても誰も参加しません。**課金されるのは新規作成時の1回だけ**で、再実行で積み増されることはありません
- **金庫が約束できる範囲でしか賞金は付きません**: 賞金は作成時に金庫から引かれるのではなく、精算時に払い出される「約束」です。そのため引当は、金庫の残高から**未精算マーケットに約束済みの賞金を差し引いた額**に対して行われます（`committed_seed_pool()`）。残りが足りなければ賞金は減り、0になることもありますが、払えない約束はしません。1回で数十件を作るようになった以上、ここを見ないと金庫の残高を超えて約束してしまいます
- **判定予定日時**はキックオフの3時間後に自動設定されます。その時刻を過ぎると`/tasks`に結果入力タスクとして掲示されます
- **リーグ名・節**も保存されるので、`/markets`の絞り込みで使えます

#### 実行のしかた

| 方法 | 使いどころ |
|---|---|
| `npm run sync-fixtures` | 手元から。設定を変えた直後の確認に |
| `/admin` の「⚽ 近日中の試合からマーケットを自動生成する」 | 管理者が今すぐ埋めたいとき |
| `/api/cron/tick`（日次のCron） | 本番での自動運用。**別のCron枠は不要**です（Vercelの無料プランはCron数が限られるため、精算処理と同じ枠に相乗りさせています） |
| `POST /api/cron/sync-fixtures` | 外部スケジューラから個別に叩きたいとき |

`SPORTS_API_PROVIDER`が未設定または`mock`のとき、**アプリ側からの自動生成は拒否されます**。デモ用プロバイダは実在するクラブ名で架空の対戦カードを作るため、データベースに入ると本物の日程と見分けがつかず、行われない試合に予想が集まってしまうからです。CLIからは（意図的な操作なので）警告つきで実行できます。

万一ダミー試合が作られてしまった場合は、次のコマンドで中止・返金できます。

```bash
npm run remove-mock-markets            # 確認のみ
npm run remove-mock-markets -- --apply # 中止＋全額返金を実行
```

取り込みに失敗しても精算処理は成功したまま、失敗理由だけがレスポンスに載ります。

### 結果の自動取得

終了した試合のスコアをAPIから取得し、マーケットの結果として報告します。**即時に確定させるのではなく**、人が報告するときと同じ異議申し立て期間（既定24時間、`SPORTS_API_DISPUTE_WINDOW_MINUTES`）を通ってから精算されます。APIも間違えますし、中止・再試合・スコアの訂正は実際に起きるので、機械が報告したというだけで異議を挟む余地をなくすのは筋が悪いためです。

対象は**キックオフ時刻を過ぎた自動生成マーケット**（`status = 'locked'`）だけです。

実行経路は3つで、いずれも同じ本体（`scripts/sports-api/syncResults.mjs`）を呼びます。

| 経路 | いつ |
|---|---|
| 日次Cron `/api/cron/tick` | 毎日自動。設定不要 |
| `/admin` の「🏁 終了した試合の結果を取り込む」 | 待たずに今すぐ確認したいとき |
| `npm run sync-results` | 手元から |

報告された結果には**証跡URL**（TheSportsDBの試合ページ）が自動で付きます。人が報告するときは証跡が必須なので、APIが報告するときだけ出どころ不明では、あとから誰も検証できません。

Cronでは**結果の取得を精算スイープより先**に実行します。夜のうちに終わった試合が、その場で報告され、異議申し立て期間が既に過ぎていれば同じ実行の中で精算されるためです（順序が逆だと丸一日待つことになります）。

> **注意**: 1試合の取得に失敗しても他は続行します。1件のデータ不備で残り全部の精算が止まらないようにするためで、失敗件数は実行結果に出ます。

> **API-Footballについて**: 以前から入っている`api_football`プロバイダも使えますが、**無料プランは現行シーズンを取得できません**（`"Free plans do not have access to this season, try from 2022 to 2024."`）。現行シーズンを扱うなら有料プランが必要です。上記のTheSportsDBを推奨します。

#### 試合が更新されないときのチェックリスト

APIキーを設定したのに実際の試合が入ってこない場合、原因はほぼ次の3つです。

1. **`SPORTS_API_PROVIDER=mock` のままになっている** — キーを入れただけでは切り替わりません。`api_football` に変更するか、この行ごとコメントアウトしてください（キーがあれば自動で`api_football`を選びます）。この状態のときスクリプトが警告を出すようにしてあります。
2. **プランが対象外のシーズンを指定している** — API-Footballの無料プランは過去の特定シーズンしか含まれておらず、対象外シーズンはエラーではなく「0件」で返ってきます。`https://v3.football.api-sports.io/leagues?id=98` で自分のプランが使えるシーズンを確認し、`API_FOOTBALL_SEASON`に設定してください。
3. **単に実行していない** — `npm run sync-fixtures` は手動またはcronで動かす必要があります。

スクリプトはリクエストURL・取得件数・残りAPIクォータ・0件時の警告を出力するので、上記のどれに当たっているか判別できます。

### マイクロワーク市場 — 広告と、それ以外の仕事をポイントの原資にする

これまでのタスク（広告視聴・アンケート）は、`complete_task`がユーザーと金庫に同額を加算するだけで、**そのポイントを裏付ける現金がどこにもありませんでした**。実際に回したいのは逆で、

```
広告主・代理店・発注者  ──(円)──▶  運営  ──(ポイント)──▶  ユーザー
```

という流れです。ポイントは「労働が価値を生んだ」という建前ではなく、**実際に受け取った円を原資に発行される**ようになります。

#### 円とポイントは別の台帳に置く

これが一番重要な設計判断です。`treasury_logs`は**ポイントだけ**の台帳のまま変えていません。円は`campaigns` / `campaign_payments` / `task_completions.revenue_yen`側だけで扱い、突き合わせは`campaign_economics`ビューが行います。ひとつの台帳に2つの通貨を混ぜると、あとから残高の意味を誰も説明できなくなります。

#### 構成

| テーブル | 役割 |
|---|---|
| `sponsors` | 広告主・代理店・業務委託の発注者。1社が複数の案件を持つ |
| `campaigns` | 1件の商談。1件あたりの受取額・固定額・予算上限・件数上限・期間 |
| `campaign_payments` | 実際に入金された円。発生額と分けて持つことで「請求漏れ」が見える |
| `tasks.campaign_id` ほか | タスクがどの案件に紐づくか、検収方法、クールダウン、募集件数 |
| `task_peer_reviews` | 相互チェック（quorum）の1票 |

管理画面は`/admin/work`です。スポンサー → 案件 → タスクの順に作り、**案件を「稼働」にするまでタスクは`/tasks`に出ません**。広告主から取り下げの連絡が来たら、その案件を一時停止するだけで、ぶら下がるタスクがすべて受付を止めます。

#### 検収方法（`tasks.verification_mode`）

新しい仕事を出すときに一番効いてくる設定です。人の作った成果物を無検収で支払うと、**そのタスクはその日のうちにポイント製造機になります**（空欄で提出しても報酬が出るので）。

| モード | 挙動 | 使いどころ |
|---|---|---|
| `auto` | 提出と同時に支払い | 広告ネットワークのSSVなど、外部が既に検証済みのものだけ |
| `quorum` | 他のユーザーが規定人数OKを出したら支払い | **件数の多いマイクロワークの基本**。運営が1件ずつ見るやり方は件数で破綻する |
| `review` | 管理画面で1件ずつ承認したときに支払い | 単価が高い・件数が少ない作業 |
| `none` | 検収せず即時払い | 原資のない社内向け販促タスクだけ |

相互チェックの安全側は、自分の提出は自分でチェックできない・1提出につき1人1票・規定数の否認で却下、の3点をRPC側（`peer_review_completion`）で担保しています。またチェックする側にも報酬（`review_reward_points`）が要ります。無償にすると誰も見に行かず、提出が保留のまま溜まり続けるだけなので、**チェック報酬0の`quorum`タスクは管理画面が作成を拒否します**。

#### 採算 — チェック報酬まで含めた原価で見る

`campaign_economics`ビューが案件ごとに「発生額（作業が終わった分の受取額）」「入金額」「付与ポイントの原価」を並べます。原価には**相互チェックの報酬も含めます**。報酬30pt・チェック2pt・3人必要なタスクなら、1件あたりの原価は30ptではなく36ptで、ここを見落とすと黒字のつもりの案件がずっと赤字で回り続けます。管理画面のタスク作成フォームも同じ計算をして、受取額を超えていれば「逆ざや」と警告します。

`margin_yen`がマイナスの案件は、続けるほど運営が損をします。

#### 使いすぎの止め方

案件の予算（`budget_yen`）と件数（`max_completions`）は**提出を受け付ける時点で**判定します。作業させてから「予算切れなので払えません」が一番まずいためです。上限を両方とも空にすると、受注額を超えて作業させてもアプリは止めません。却下した提出は予算を消費しない（`revenue_yen`が0に戻る）ので、その枠は他の人に回ります。

そのほか、タスク単位で「1人あたりの上限」「全体の募集件数」「再実行の間隔（クールダウン）」を設定できます。

#### 新しい種類の仕事を出す

コードを書く必要はありません。提出フォームの項目は`tasks.config.fields`にJSONで書きます（管理画面に種類ごとの雛形が入っています）。

```json
{
  "instructions": "対象の店舗の外観を撮影し、アップロード先のURLを貼ってください。",
  "fields": [
    { "id": "photo_url", "label": "写真のURL", "type": "url", "required": true },
    { "id": "shop_name", "label": "店舗名", "type": "text", "required": true }
  ]
}
```

`type`は`text` / `textarea` / `url` / `number` / `select` / `checkbox`が使えます。種別のラベルと雛形は`lib/workKinds.ts`にあり、データ分類・文字起こし・翻訳・写真提出・現地確認・AI出力の評価・動作テストなどを最初から並べてあります。

#### 広告ネットワークとつなぐ場合

`app/api/webhooks/ad-reward/route.ts`が、HMAC署名付きのSSV（Server-Side Verification）コールバックの参照実装です。広告ネットワーク側から`user_id` / `task_id` / `transaction_id` / `signature`を受け取り、`AD_NETWORK_SSV_SECRET`で検証してから`complete_task`を呼びます。この経路のタスクだけが`verification_mode = 'auto'`にしてよい対象です。

#### 法務まわりで先に確認すべきこと（未対応）

実装ではなく運用の話ですが、原資が実際のお金になる以上、公開前に確認が必要です。

- **資金決済法**: ポイントを換金・第三者への譲渡ができない前提を崩さないこと。換金性を持たせると前払式支払手段や資金移動業の話になります
- **景品表示法**: 「◯◯するとポイント」という表示が景品規制・有利誤認にあたらないか（特に広告主のキャンペーンをそのまま転載する場合）
- **業務委託か労働か**: 継続的・指揮命令的なマイクロワークは労務性が問題になりえます。単発・自由参加の建て付けを崩さないこと
- **個人情報保護法**: アンケート・現地確認で個人情報を集める場合の利用目的の明示と、広告主への提供の可否
- **広告主との契約**: 成果の定義（何をもって1件とするか）、不正時の返金条項、支払サイト

### 動作確認用のモックタスク

実装済みのタスク経路をひととおり触れるダミーを投入できます。

```bash
npm run seed-mock-tasks             # 投入する
npm run seed-mock-tasks -- --remove # 片付ける
```

入るのは4種類で、それぞれ違う支払い経路を通ります。

| タスク | 検収 | 動き |
|---|---|---|
| 動画広告を見る（3秒） | `auto` | 全画面のポップアップが3秒→閉じると即10pt |
| アンケートに答える | `auto` | 2問回答で即50pt |
| ニュースをジャンル分けする | `quorum` | 提出→他の2人がOK→30pt（チェック側にも2pt） |
| 使いにくかった画面を報告する | `review` | 提出→`/admin/work`で承認→80pt |

ダミーのスポンサーと案件（1件100円の受取という想定）にも紐づくので、タスクを触ると`/admin/work`の採算表にも数字が動きます。

タイトルはすべて `[デモ]` で始まります。**以前モックの試合データが本番に混ざって実在しない試合のマーケットができたことがあり**、モックは見た目で判別できないと本物として扱われてしまうためです。`--remove` の判定もこの接頭辞ひとつに寄せてあります。

なお `--remove` は、**提出実績のあるタスクは削除せず停止**します。報酬が付いたタスクを行ごと消すと、台帳に残高の変動だけが残って理由が辿れなくなるためです。

#### 動画広告のモックについて

`components/AdTaskButton.tsx` が実際の動画リワード広告の「形」を再現しています。全画面を覆う・規定秒数はスキップできない・再生完了後に報酬、という順序は本物と同じで、実SDKに差し替えるときに変わるのは `start()` の中だけです。

ただし**このモックはクライアントの「見終わりました」を信じてポイントを付与しています**。本番では`/api/tasks/[taskId]/complete`を直接叩けばポイントが増えてしまうので、報酬の確定は広告ネットワークのSSVコールバック（`app/api/webhooks/ad-reward`）側に移す必要があります。

### 法務ページと運営者情報（広告収益化の前提）

広告ネットワーク・ASPの審査は、まずこの4ページの有無を見ます。

**β版の間、フッターの導線は既定で非表示**にしてあります（`SHOW_LEGAL_FOOTER=true`で表示）。各ページはURLで常に開け、マイページの下部からもたどれます。一般公開時と広告の申し込み前には必ず`true`にしてください — 審査は「どのページからでもプライバシーポリシーに到達できるか」を見ます。

| ページ | 内容 |
|---|---|
| `/terms` | 利用規約。**第1条にポイントの性質**（換金・購入・譲渡ができないこと）を置いています |
| `/privacy` | プライバシーポリシー。取得する情報・利用目的・第三者提供・Cookieと広告配信・外部送信 |
| `/operator` | 運営者情報。特商法表記との関係もここに書いています |
| `/contact` | お問い合わせフォーム。未ログインでも送信できます |

利用規約の第1条を最初に置いているのは体裁の問題ではありません。**本サービスが賭博にあたらない理由そのもの**なので、ここを崩す変更（換金・ポイント販売・アカウント間送付）を入れる場合は、法的な位置づけが根本から変わります。

#### 運営者情報は環境変数で入れる

会社名・所在地・連絡先は `.env`（本番なら Vercel の Environment Variables）から読みます。ソースに直書きしていないのは、**法務ページで一番危険なのが「体裁は整っているが中身が嘘」の状態**だからです。サンプルの会社名が入ったまま公開されたプライバシーポリシーは、何も無いより悪い。

```
OPERATOR_NAME=        # 運営者名
OPERATOR_ADDRESS=     # 所在地
OPERATOR_CONTACT_EMAIL=
SITE_URL=
```

この4つのどれかが未設定だと、各ページの先頭に**赤い警告が表示され**、未記入のまま公開されていることが一目で分かるようにしてあります。広告の申し込み前に必ず埋めてください。

#### プライバシーポリシーに追記が必要な箇所

「5. 利用者情報の外部送信について」は**枠だけ**用意してあり、中身は空です。広告やアクセス解析を導入したら、送信先の事業者名・送信される情報・利用目的・各社のポリシーへのリンクを追記してください。国内向けサービスで外部の広告事業者にブラウザから直接情報が送られる構成では、この開示が必要になります。

### エラーメッセージ

マーケット作成やベットが失敗したとき、RPCが投げる例外（`insufficient_balance`・`market_not_open`・`already_bet_other_outcome`など）は`lib/errorMessages.ts`で日本語の説明に変換され、その理由が画面に表示されます。「作成に失敗しました」だけで終わらせず、**残高が足りないのか、締切を過ぎたのか、選択肢の作り方が不正なのか**が分かるようにしています。ログイン切れ（401）の場合はログイン画面へ誘導します。

想定していないエラーでも黙り込まないようにしてあります。

- APIは必ずJSON（`{ error, detail }`）を返します。以前は想定外の例外がNext.jsのHTMLエラーページになり、JSONを期待しているフォーム側がパースに失敗して「失敗しました」としか出せませんでした
- 日本語訳を用意していないエラーコードは、原文を`（理由: ...）`として併記します
- バリデーション失敗は、対応する説明文がない項目でも**項目名**を出します

操作が失敗したのにJSONすら返ってこなかった場合（ルートのコンパイルエラー、開発サーバーの停止など）は、HTTPステータスを理由として表示します。例: 「マーケットを作成できませんでした。（理由: HTTP 500 — サーバーがエラーページを返しました。npm run dev のターミナルにエラーが出ていないか確認してください）」

#### 「◯◯できませんでした」が出たら

原因の大半は**アプリだけ更新してDBを更新していない**ことです（`git pull`のあとに`npm run migrate`を忘れた状態）。この場合、コードが呼ぶ関数や列がDBに存在せず、Postgresは`function ... does not exist`という、状況を知らない人には意味の分からないメッセージを返します。

そこで2段構えで検出しています。

- **画面上部の警告バー**: 起動時に`supabase/migrations/`のファイル一覧と`schema_migrations`テーブルを突き合わせ、未適用があれば全ページの上部に「`npm run migrate` を実行してください」と未適用ファイル名を表示します（`lib/schemaCheck.ts`）
- **操作時のメッセージ**: RPCがPostgresの`42883`（関数が無い）/`42703`（列が無い）/`42P01`（テーブルが無い）を返した場合、`schema_out_of_date`として同じ案内を出します（`lib/rpc.ts`）

理由が「HTTP 500」とだけ出る場合は、DBではなくビルドの問題です。**アプリを止めて`.next`を消してから起動し直してください**。開発サーバーを動かしたままファイルを上書きコピーすると、`.next`のキャッシュが壊れて特定のAPIだけがHTMLのエラーページを返すことがあります。

```bash
# Ctrl+C でアプリを止めてから

# macOS / Linux
rm -rf .next

# Windows (PowerShell) — rm -rf は使えません
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue

npm run dev
```

### 更新はZIPの上書きではなくgit pullで

GitHubの「Download ZIP」で取得したフォルダ（`claude-main`）に新しいZIPを上書き展開する運用は、削除されたファイルが残る・アプリ稼働中にファイルが差し替わって`.next`が壊れる、といった形で**原因の分かりにくい不具合になります**。`git clone`しておけば`git pull origin main`だけで済み、削除も正しく反映されます。

```bash
git clone https://github.com/Nobutaka-Takuma/claude.git
cd claude
npm install
cp .env.example .env.local   # 既存の .env.local があればそれをコピー
npm run migrate
npm run dev
```

## 一般公開にあたっての倫理的リスクと対応

「誰でもマーケットを作れる」ことがこのアプリの価値ですが、同時に**このアプリが「特定の人が死ぬかどうか」に賭ける場になりうる**ということでもあります。ここでは想定されるリスクと、実装済みの対応を並べます。

### 何が問題になりうるか

| リスク | なぜ問題か | 対応 |
|---|---|---|
| **人の死傷・事件の発生を対象にする** | 予想が的中の動機を作る。当事者にとっては自分の生死が賭けの対象になる | 作成時に**自動拒否**（`lib/contentPolicy.ts`）。加えて通報対象 |
| **私人のプライバシー** | 公人でない個人の交際・病気・離婚などは、本人の同意なく晒される | ガイドラインで禁止＋通報カテゴリ「私人のプライバシー」 |
| **差別・ヘイト** | 特定属性への侮辱が「予想」の形で正当化される | ガイドラインで禁止＋通報カテゴリ |
| **未成年に関するもの** | 保護の必要性が高く、本人に選択権がない | ガイドラインで禁止＋通報カテゴリ |
| **結果を操作できるマーケット** | 当事者が賭けてから結果を動かせる（八百長と同じ構造） | 通報カテゴリ「結果を操作できる」。判定に証跡URLを必須化 |
| **判定できないマーケット** | 決着がつかず、判定者の主観で誰かの持ち点が動く | 通報カテゴリ「判定できない」。作成時に判定予定日時を必須化 |
| **賭博性・射幸心** | 金銭を賭ける行為と誤解される／依存を助長する | ポイントは**換金不可・購入不可・送付不可**。ガイドライン冒頭に明記 |
| **判定の多数派による横暴** | 多数決が事実より強くなる | 判定には保証金と証跡URLが必要。誤った判定は保証金没収 |
| **通報の悪用（冤罪BAN）** | 少数の結託で正当なマーケットを潰せる | 1人1通報、自作自演の禁止、運営による**通報の却下**（却下後はそれまでの通報が無効化） |
| **報告者・通報者への報復** | 誰が通報したか分かると報復される | 通報者はRLSで本人と運営にしか見えない |

### コミュニティによるマーケットの停止（通報→BAN）

ガイドラインに反するマーケットは誰でも通報できます。**通報が3件（`MARKET_BAN_THRESHOLD`）に達した時点で、そのマーケットは即座に停止**されます。運営の判断を待つ設計にしなかったのは、担当者が寝ている間もマーケットは動き続けるからです。

```
誰かが通報（理由カテゴリ＋任意の補足）
   ↓ 3件に到達
即座に停止（同一トランザクション内で実行）
   ├ 予想したポイントは全員に全額返金
   ├ 作成者の作成料100ptは没収（返金されない）
   ├ 通報した人に3pt（REPORT_REWARD）ずつ
   └ 結果報告・異議申し立ての保証金は預けた人に返却
```

金額の設計意図は次のとおりです。

- **作成料は返金しない**。試合中止などの正当な理由で中止（void）した場合は返金されますが、規約違反での停止で返ってくるなら、禁止されたマーケットを試しに立てるコストがゼロになります
- **予想した人には全額返す**。ルールを破ったのは作成者であって、賭けた人ではありません
- **通報者への報酬は少額**。通報の手間に見合う程度で、かつ「報酬目当ての濫用」に見合わない額にしています

**逆方向の攻撃**（3アカウントで結託し、正当なマーケットを潰して報酬を得る）への対策は3つです。

1. 通報は1人1回、かつ**自分のマーケットは通報できない**
2. 報酬が作成料の分け前ではなく少額の定額
3. 運営が**通報を却下**できる。却下するとそれまでの通報は集計から外れるので、同じグループが「あと1票」で停止させることはできません（`/admin` の通報キューから操作）

閾値はコミュニティの規模に対する調整項目です。3という数字は「3人が独立に問題だと判断した」が意味を持つ小規模コミュニティ向けで、ユーザーが増えたら`MARKET_BAN_THRESHOLD`を上げてください。

### 作成時点での自動拒否

通報は本質的に事後対応で、3人が気づくまでマーケットは公開され、賭けられ続けます。**短時間でも公開されること自体が害になる主題**については、作成時点で拒否します（`lib/contentPolicy.ts`）。

対象は「人の死亡・死傷」「自殺」「テロ・襲撃・暗殺」「未成年の性的搾取」に関する語です。

これは単純な文字列マッチであり、**内容フィルタとしては不完全**です。言い換えれば回避できますし、逆に無害なもの（フィクションの登場人物の生死など）を誤って弾くこともあります。それでも置いているのは、明らかなケースが一度も公開されないようにするためで、取りこぼしは通報による停止が受け止めます。誤判定された場合は運営に連絡してもらう旨をメッセージに含めています。

### ガイドライン

`/guidelines` に公開しています。作成フォームからもリンクしており、「作ってはいけないもの」と「良いマーケットの条件」、ポイントが換金できないこと、通報と停止の帰結を明記しています。

### 未対応（運用開始前に検討が必要）

- **年齢確認**：申告も確認も行っていません。利用規約に下限年齢（`MINIMUM_AGE`、既定13歳）と保護者の同意が必要な年齢（`PARENTAL_CONSENT_AGE`、既定18歳）は明記していますが、実際に確認する仕組みはありません。予測市場に見た目が近いサービスなので、18歳以上に限定する判断もありえます
- **通報者・作成者の累犯管理**：同じユーザーが繰り返し違反しても、アカウント単位の制限はありません
- **多重アカウント対策**：メールアドレスのみで登録できるため、通報の閾値も賛成投票の閾値も多重登録で操作できます。公開時にはメール確認やレート制限が必要です
- **問い合わせへの返信**：受信と管理画面での対応管理は実装済みですが、返信はメールソフトから手動で行う必要があります（送信メールの仕組みは未実装）

公開手順とあわせた公開前チェックリストは [`docs/DEPLOY.md`](./docs/DEPLOY.md) にあります。
