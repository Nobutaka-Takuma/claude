# Prediction Market DAO — MVP

Polymarket / みらいマーケット的な、労働（広告視聴・アンケート）で貯まるコミュニティ金庫（Treasury）を原資に、サッカーの試合結果からYes/No質問・複数選択肢の問いまで自由に予測できるパリミュチュエル方式のWebアプリのMVP。

設計ドキュメント一式は [`docs/`](./docs) を参照してください（DBスキーマ解説・バックエンドロジック解説・ワイヤーフレーム）。

## 技術スタック

- Next.js (App Router) / TypeScript / Tailwind CSS
- Postgres（Supabase向けに書かれたスキーマ・RPC関数一式を、ローカルではSupabaseプロジェクトの代わりに素のPostgresへ直接適用して動かしています。本番でSupabaseプロジェクトを使う場合は`supabase/migrations/00000000000000_local_dev_auth_shim.sql`だけは適用しないでください — それ以外はSupabase CLIでそのまま`supabase db push`できます）

## セットアップ（ローカル開発）

前提: Node.js 20+、ローカルにPostgres 16が起動していること。

```bash
# 1. 依存関係のインストール
npm install

# 2. DBを作成
createdb prediction_market

# 3. 環境変数を用意（デフォルトのままでOK。スポーツAPI連携はキーなしのモックプロバイダで動きます）
cp .env.example .env.local

# 4. マイグレーションを適用（未適用のものだけが実行されます）
npm run migrate

# 5. デモ用データを投入（管理者アカウント・タスク・マーケットのseed）
npm run seed
npm run seed-news   # News-Firstフィード(/news)検証用のデモ記事＋紐付けマーケット（任意）

# 6. 開発サーバーを起動
npm run dev
```

http://localhost:3000 を開くとアプリが動きます。

## 実装済み機能

- 認証（サインアップ / ログイン / セッションCookie）。新規登録時に金庫から**1000ptのウェルカムボーナス**（`SIGNUP_BONUS_POINTS`）
- **マーケットメイカー経済圏**: ユーザーが100pt（`MARKET_CREATION_COST`）を支払うとマーケットを即公開でき、そのマーケットが精算されるとテラ銭の10%（`MARKET_CREATOR_FEE_BPS`）が作成者の報酬になります。盛り上がるほど作成者の取り分が増えるので、人気の出るお題を作るインセンティブが働きます。無料の「提案＋賛成投票」経路も残していますが、そちらに作成者報酬はありません（後述）
- タスクセンター: 広告視聴（デモ版はシミュレーション再生）・アンケート回答 → `complete_task` RPCで自動ポイント付与＆金庫更新
- マーケット一覧・詳細・パリミュチュエル方式のベット（`place_bet` RPC）。**的中者には賭けた分が必ず全額戻り**、そのうえで他の選択肢のプールから運営手数料(テラ銭)を除いた分を山分けします。他の選択肢に誰もベットしていなければ手数料もかからず、賭けた分がそのまま戻ります（後述）
- **ベットの取り消し**（`cancel_bet` RPC）: 締切前なら3pt（`BET_CANCEL_PENALTY`）のペナルティを引いて返金されます。また**同じマーケットで別の選択肢に賭けることはできません**（両建てで確実に取り分を得る抜け道を塞ぐため）
- **関連マーケットの表示**: ベット画面の下部に、同じニュース → 同じリーグの同節 → 同じリーグ → 同じカテゴリ、の優先順で関連するオープン中のマーケットを表示します
- **お題の形式は自由**: 試合の勝敗（ホーム/引分/アウェイ）だけでなく、Yes/No質問（例:「開幕戦で〇〇選手はスタメン出場するか？」）や、2〜8個の任意の選択肢を持つマーケットも作成できます（`markets.market_kind` + `outcome_options`）
- お題提案 → 賛成票が閾値（既定3票、`MARKET_APPROVAL_THRESHOLD`で変更可）に達すると自動オープン
- **コミュニティ判定（保証金付きOptimistic Oracle）**: 結果の判定は**誰でも提案できます**。提案後24時間（`DISPUTE_WINDOW_MINUTES`）以内に異議が出なければ自動確定・精算、異議が出ればDAO投票の多数決で最終決定します（`finalize_expired_markets` RPCが`sync_market_status`と同様にマーケット閲覧のたびに遅延実行される簡易cron）。詳細は後述
- **早期確定（締切前の判定）**: 結果がキックオフ前に判明した場合、100pt（`EARLY_RESOLUTION_BOND`）を預けてベットを即座に停止し、3時間（`EARLY_RESOLUTION_VOTING_HOURS`）のDAO投票にかけられます（後述）
- **判定投票の報酬**: 正解の選択肢へ投票した人のうち先着10名（`VOTE_REWARD_SLOTS`）に3pt（`VOTE_FLAT_REWARD`）、さらに正解者全員でテラ銭の50%（`VOTER_RAKE_SHARE_BPS`）を按分。10票集まるまでは`/tasks`に「タスク」として表示されます
- 管理者による緊急オーバーライド（オラクルをスキップした即時確定・全額返金での中止）
- **RSSニュース取り込み**（`scripts/sync-news.mjs`）: Yahoo!ニュース・NHKなどのRSSから記事を取り込み、`/news`フィードに表示。常駐更新（`--watch`）と画面上の更新ボタン／APIエンドポイントに対応（後述）
- **スポーツAPI連携**（`scripts/sync-fixtures.mjs` / `scripts/sync-results.mjs`）: 試合予定の自動取得・マーケット自動生成と、試合結果の自動取得（**ただし無料プランでは現行シーズンが取得できません**。後述）
- マイページ（ベット履歴・ポイント履歴）
- 金庫（Treasury）ダッシュボード（公開・収益源の内訳）

### 初期賞金（シード）— 最初のベットに意味を持たせる仕組み

stake-back保証があるため、誰もベットしていないマーケットに賭けても「損はしないが得もしない」状態になり、最初にベットする動機がありませんでした。

そこで**作成料100ptのうち90pt（`MARKET_SEED_BPS`、既定90%）を「初期賞金」としてマーケットに積む**ようにしています。この賞金は精算時に的中者へ上乗せ分配されるため、反対側に誰もいなくても勝てばポイントが増えます（100pt賭けて的中なら190pt）。残り10ptが運営手数料です。

金庫は作成時に100ptを預かり、精算時に90ptを的中者へ払い出す「預かり役」になります（`market_seed_payout`として台帳に記録）。マーケットが中止された場合は作成料が全額返金され、賞金は払い出されません。

### パリミュチュエル配当の仕組み（stake-back保証）

他の選択肢に誰も賭けていない場合でも的中者が損をしないよう、テラ銭は「他の選択肢（外れた側）のプール」からのみ徴収します。

- 総プール = 的中した選択肢のプール + 他の選択肢のプール合計
- テラ銭 = 他の選択肢のプール合計 × 手数料率（既定10%）
- 的中者への配当 = 自分の賭け金（全額） + 自分の賭け金 ÷ 的中した選択肢のプール × (他の選択肢のプール合計 − テラ銭)

他の選択肢のプールが0（誰も逆張りしていない）なら、テラ銭も0になり、賭けた分がそのまま戻ります。

### マーケットの作り方（2つの経路）

| | 有料（推奨） | 無料 |
|---|---|---|
| コスト | 100pt（金庫へ） | 0pt |
| 公開まで | **即時** | 賛成3票が集まるまで |
| 作成者報酬 | テラ銭の**10%** | なし |
| 入口 | `/news` の各記事、または `/markets/propose` | `/markets/propose` |

有料経路では、精算時のテラ銭（外れた側のプールの10%）がさらに分割され、その10%が作成者に、残り90%が金庫に入ります。マーケットが中止（void）になった場合は、作成者に非がないため作成料100ptは返金されます。

### マーケットの形式（お題の種類）

3種類のお題を作成できます。

| market_kind | 内容 | outcome_options の例 |
|---|---|---|
| `match_winner` | 試合の勝敗（3択） | ホーム/引分/アウェイをチーム名から自動生成 |
| `binary` | Yes/No質問 | `[{"key":"yes","label":"はい"},{"key":"no","label":"いいえ"}]` |
| `multi_outcome` | 自由な複数選択肢（2〜8個） | 提案者が入力したラベルから生成（`key`は`opt1, opt2, ...`） |

ベット・配当計算・Optimistic Oracle・DAO投票はすべて`outcome_options`ベースの汎用ロジックで動作するため、選択肢の数や種類に関わらず同じ仕組みで扱えます。

作成時には以下も指定できます。

- **カテゴリ**（サッカー / 野球 / 経済 / 金融・為替 / 政治 / テック / エンタメ など）— 一覧のフィルタとアイコンに反映されます
- **結果判定の予定日時** — ベット締切とは別に「いつ結果が分かるか」を示せます
- **大会・リーグ／第何節**（スポーツカテゴリのみ）— 後述の検索で使います

### スポーツの試合マーケットを探しやすくする

試合予定APIが有料のため、スポーツのマーケットはユーザーが手で作ることになります。そのままだと同じ試合が重複したり探せなくなるので、**大会・リーグと第何節を構造化データとして持たせて検索できる**ようにしました。

- `/markets` にキーワード検索（チーム名・リーグ名・タイトル・説明を対象）
- カテゴリ、リーグ、第◯節での絞り込み（実在するものだけがチップとして出ます）
- マーケット詳細のカテゴリ/リーグ/節タグからも同じ絞り込みに飛べます

日本語のためPostgresの全文検索（tsvector）ではなくILIKEによる部分一致にしています。件数が増えた場合は`pg_trgm`+GINインデックスへの移行が適切です。

### 結果の判定 — コミュニティ判定（保証金付きOptimistic Oracle）

**なぜ人力なのか**: 当初はスポーツAPIで自動判定する想定でしたが、API-Footballの無料プランは現行シーズンにアクセスできませんでした（`"Free plans do not have access to this season, try from 2022 to 2024."`）。そもそもユーザーが作る任意のお題（「〇〇選手はスタメンで出るか」など）はどのAPIでも判定できません。そこで判定を人に戻し、Optimistic Oracleで担保する設計にしています。

```
ベット締切（キックオフ通過で自動ロック）
   ↓  誰でも「結果はこれ」と提案できる（保証金 100pt を預託）
提案中（pending_resolution）
   ↓  24時間以内に異議なし          ↓ 異議あり
自動で確定・精算                    DAO投票の多数決で決定
保証金は提案者に返却                 提案が支持されれば返却 / 覆されれば没収
```

保証金（`RESOLUTION_BOND`）は、**自分のベットに有利な結果を提案して誰も気付かないのを狙う**攻撃を防ぐためのものです。嘘をつく利益より没収額が大きければ割に合わなくなるので、運用に合わせて調整してください。

#### 締切前に結果が判明した場合（早期確定）

「試合前に出場停止が発表された」「開催そのものが中止になった」のように、キックオフを待たずに答えが確定することがあります。締切まで放置すると、結果を知っている人だけが賭けられる時間ができてしまうため、**誰でも100pt（`EARLY_RESOLUTION_BOND`）を預けて即座にベットを止め、判定にかけられる**ようにしました。

```
オープン中（まだベット可能）
   ↓  「早期確定を申請」（保証金 100pt を預託）
ベット即停止（disputed / resolution_source = community_early）
   ↓  3時間のDAO投票（EARLY_RESOLUTION_VOTING_HOURS）
多数決で確定・精算
申請が支持されれば保証金は返却、覆されれば没収
```

投票の締切が来ると、マーケット閲覧時の遅延cron（`finalize_expired_markets`）が多数決を集計して精算まで進めます。票が1票も入らなかった場合は申請どおりに確定し、保証金は返却されます。

#### 保証金の没収と分配

異議申し立て（通常の異議・早期確定への反対のいずれも）にも**同額の保証金（`CHALLENGE_BOND`）が必要**です。無料だと精算の引き延ばしがタダになってしまうためで、これによって「提案者 vs 異議申立者」が同じ額を賭けて争う形になります。

DAO投票で負けた側の保証金100ptは没収され、**その70%（`BOND_AWARD_BPS`）が勝った側へ、残り30%が金庫**に入ります。

| 結果 | 提案者 | 異議申立者 |
|---|---|---|
| 提案が支持された | 保証金100pt返却 ＋ 70pt獲得 | 保証金100pt没収 |
| 提案が覆された | 保証金100pt没収 | 保証金100pt返却 ＋ 70pt獲得 |

#### 判定投票の報酬

判定を人に任せる以上、「投票する理由」が必要です。そこで**正解の選択肢に投票した人**に2種類の報酬を出します。

- **先着ボーナス**: 正解に投票した人のうち先着10名（`VOTE_REWARD_SLOTS`）に3pt（`VOTE_FLAT_REWARD`）ずつ
- **テラ銭の按分**: 正解に投票した人**全員**で、そのマーケットのテラ銭の50%（`VOTER_RAKE_SHARE_BPS`）を頭割り

精算時のテラ銭は、作成者報酬（10%）→ 投票者への按分（50%）→ 残りが金庫、の順に分割されます。

投票がまだ足りないマーケットは`/tasks`に「結果確定の投票」として広告視聴・アンケートと並んで表示されます。**先着枠は「正解者のうち10名」ですが、投票中は誰が正解かは分からない**ため、タスクとしての掲載条件は「総投票数が10票未満」にしています。

### RSSニュース取り込み

```bash
npm run sync-news              # 1回だけ取り込む（guid/linkで冪等）
npm run sync-news -- --watch   # 常駐して定期的に取り込む（既定30分間隔）
npm run sync-news -- --watch 15  # 15分間隔
```

- 初期設定はYahoo!ニュース（経済/スポーツ/国内/IT）とNHK（経済/スポーツ）です（`scripts/news-sources/feeds.mjs`）。**配信元はフィードURLを予告なく変更・廃止するため、実際に取得できるかは各自でご確認ください**。スクリプトはフィードごとに成否を表示するので、死んでいるフィードは黙って無視されず分かるようにしてあります。
- `NEWS_FEEDS`環境変数にJSONを渡せば、フィード一覧をまるごと差し替えられます。
- RSS 2.0 / RDF(RSS 1.0) / Atom の3形式に対応しています（日本の配信元はRDFもまだ使っています）。
- 取り込んだ記事は`/news`に表示され、ユーザーがそこからマーケットを作成できます。

定期更新の方法は3通りあります。用途に応じて選んでください。

| 方法 | 使いどころ |
|---|---|
| `npm run sync-news -- --watch` | ローカル開発。既定間隔は`NEWS_SYNC_INTERVAL_MINUTES`（30分）。前回の取り込みが終わってから次の待機に入るので、遅いフィードでも多重実行になりません |
| `/news`の「🔄 ニュースを更新」ボタン | 管理者がその場で最新化したいとき。取り込み件数と失敗フィード数が画面に出ます |
| `POST /api/news/sync` | 外部スケジューラ（cron / GitHub Actions / Vercel Cron等）から叩く。セッションの代わりに`x-news-sync-secret`ヘッダで`NEWS_SYNC_SECRET`を渡します（未設定なら管理者セッションのみ） |

> このセッションの開発環境は外部への通信が遮断されているため、**実際のYahoo!/NHKのフィードに対する接続確認はできていません**。パーサ・取り込み・冪等性・フィード失敗時の挙動は、ローカルに立てたHTTPサーバ経由のサンプルフィード（RSS/RDF/Atom各形式）で検証済みです。

### スポーツAPI連携（マーケット自動生成・結果自動取得）

> **注意: API-Footballの無料プランは現行シーズンを取得できません。** 実際に確認したところ `"Free plans do not have access to this season, try from 2022 to 2024."` が返ります。現行シーズンの試合を扱うには有料プランが必要です。無料のまま動作を試したい場合は`API_FOOTBALL_SEASON`を2022〜2024に設定してください（過去データでの検証用）。日常運用では、マーケットはユーザーがニュースから作り、結果は上記のコミュニティ判定で確定させる想定です。

```bash
npm run sync-fixtures   # 試合予定を取得し、markets を自動生成/更新（external_ref で冪等）
npm run sync-results    # ロック済みの自動生成マーケットの結果を取得し、一次判定を自動提出
```

- デフォルトは `SPORTS_API_PROVIDER=mock`（`.env.example`参照）で、APIキーなしで動作するダミーのJ1風フィクスチャを生成します。まず動作を確認したい場合はこのままで大丈夫です。
- 本番接続する場合は `SPORTS_API_PROVIDER=api_football` にし、[api-football.com](https://www.api-football.com/) の無料枠キーを `API_FOOTBALL_KEY` に設定してください（J1リーグをカバーする数少ない無料枠API）。`API_FOOTBALL_LEAGUE_ID`（既定98）・`API_FOOTBALL_SEASON`は同社の`/leagues`エンドポイントで実際の値を確認のうえ調整してください。
- `sync-results`は試合終了を検知しても即座には精算せず、`submit_provisional_result`経由でOptimistic Oracleの異議申し立て期間を開始します（管理者が手動確定する場合と同じ経路）。
- 本番運用では両スクリプトを1日1回程度のcron（例: `pg_cron`やGitHub Actionsのscheduled workflow、Supabase Edge Functionsのcronトリガーなど）から実行する想定です。このリポジトリには実際のスケジューラは含まれていません。

#### 試合が更新されないときのチェックリスト

APIキーを設定したのに実際の試合が入ってこない場合、原因はほぼ次の3つです。

1. **`SPORTS_API_PROVIDER=mock` のままになっている** — キーを入れただけでは切り替わりません。`api_football` に変更するか、この行ごとコメントアウトしてください（キーがあれば自動で`api_football`を選びます）。この状態のときスクリプトが警告を出すようにしてあります。
2. **プランが対象外のシーズンを指定している** — API-Footballの無料プランは過去の特定シーズンしか含まれておらず、対象外シーズンはエラーではなく「0件」で返ってきます。`https://v3.football.api-sports.io/leagues?id=98` で自分のプランが使えるシーズンを確認し、`API_FOOTBALL_SEASON`に設定してください。
3. **単に実行していない** — `npm run sync-fixtures` は手動またはcronで動かす必要があります。

スクリプトはリクエストURL・取得件数・残りAPIクォータ・0件時の警告を出力するので、上記のどれに当たっているか判別できます。

### News-Firstフィード（`/news`）

Polymarket/ミライマとの差別化として、「ニュース記事＋その場でベットできるコミュニティ予想」を1画面にまとめたフィードです。記事の取り込みはRSSで自動化済みで（上記）、**そこからどんなお題を作るかはユーザーに任せる**設計にしています（LLMによる自動お題生成は未実装）。

- `news_articles`テーブルと、任意で紐付けられる`markets.news_article_id`、記事単位のフラットな`comments`テーブルを追加（`supabase/migrations/00000000000006_news_and_comments.sql`）
- `app/news/page.tsx`: ニュース本文の下に、そのニュースに紐づくマーケットをワンタップでベットできるコンパクトなウィジェット（`BetForm`の`compact`モード、選択肢ごとにオッズを表示）として表示し、さらにその下にコメント欄を配置
- 記事から作られたマーケットの詳細画面には、元記事へ戻るリンクが出ます
- 既存のホーム画面はそのまま残し、`/news`への導線バナーを追加する形で並行提供（ホーム画面を全面置き換えていません）
- `npm run seed-news`でデモ記事2件（為替＋スポーツ）を投入でき、RSSを設定しなくてもUIを確認できます

### エラーメッセージ

マーケット作成やベットが失敗したとき、RPCが投げる例外（`insufficient_points`・`market_not_open`・`already_bet_other_outcome`など）は`lib/errorMessages.ts`で日本語の説明に変換され、その理由が画面に表示されます。「作成に失敗しました」だけで終わらせず、**残高が足りないのか、締切を過ぎたのか、選択肢の作り方が不正なのか**が分かるようにしています。ログイン切れ（401）の場合はログイン画面へ誘導します。
