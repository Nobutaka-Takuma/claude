# オファーウォール 要件定義 v2

ドラフト（v1）を、現行コードとの突き合わせと「当面は換金なし」の決定を踏まえて詰めたもの。
このファイルが正本。

**前提となる決定**

- 報酬に換金性は持たせない。出金機能は作らない（v1 第4節「出金可能額」は削除）
- オファーウォールと予測市場は同一アカウント・**同一ポイント残高**で運用する
- 円はスポンサーとの取引にのみ使い、ユーザー向けの画面には一切出さない

---

## 1. 用語の統一

v1と現行コードで語彙がずれているので、対応を固定する。以降この表の左列を使う。

| 本書 | DB / コード | 意味 |
|---|---|---|
| オファー | `tasks` | ユーザーが実行する1件の作業 |
| 案件 | `campaigns` | 発注者との1つの取引。複数のオファーを束ね、予算と単価を持つ |
| 発注者 | `sponsors` | 企業・代理店・依頼者 |
| 提出 | `task_completions` | 1人のユーザーによる1回の作業結果 |
| 相互チェック | `task_peer_reviews` | 他のユーザーによる検収の1票 |
| 検収 | `verification_mode` | 提出を報酬に変える判定。auto / review / quorum / none |

「タスク」はUI上の呼称として `/tasks` に残っているが、本書では使わない。

---

## 2. 報酬（v1 第4節の差し替え）

### 2.1 換金しない

報酬はポイントのみで、現金・電子マネー・商品と交換できない。これは利用規約 第1条であり、
**予測市場が賭博にあたらない根拠そのもの**。オファーウォールの報酬に換金性を持たせると、
「働いて得た換金可能な財物を予測市場に賭ける」状態になり、同一残高で運用する限り
この根拠が崩れる。

将来換金を導入する場合、最低でも次のいずれかが必要になる（本書の対象外）。

- WORK報酬とPREDICT残高を**完全に別の台帳**に分け、相互の交換を一切禁止する
- 予測市場を切り離す

### 2.2 残高の区分

「出金可能額」に代えて、次の2区分を持つ。区分が必要なのは検収待ちの提出があるためで、
換金とは無関係。

| 区分 | 定義 | 実装 |
|---|---|---|
| 獲得予定 | 提出済みで検収待ち。まだ使えない | `task_completions.status = 'pending'` の `reward_points` 合計 |
| 確定 | 検収を通過し残高に入った | `profiles.points_balance`（既存） |

却下された提出は獲得予定から外れ、理由（`review_note`）とともに履歴に残る。

### 2.3 表示単位

ユーザー向けの画面・通知はすべて **pt** で表示する。円は出さない。
v1 第8節の通知例「3分・300円のタスク」は「3分・30ptのお仕事」のような表記になる。

円は `campaigns` と `campaign_economics`（管理画面のみ）で扱う。

## 3. オファーのデータ項目

### 3.1 既にあるもの

`id` / `title` / `description` / `reward_points` / `work_kind` / `verification_mode` /
`quorum_size` / `review_reward_points` / `cooldown_minutes` / `max_completions_per_user` /
`max_completions_total` / `starts_at` / `ends_at` / `campaign_id` / `config`(提出フォーム)

### 3.2 追加が必要なもの

v1 第3節の表示項目とフィルタは、これがないと成立しない。

| カラム | 型 | 用途 |
|---|---|---|
| `estimated_minutes` | int | 所要時間。一覧の表示と「pt/分」の並び替えに使う |
| `difficulty` | text | `easy` / `normal` / `hard` |
| `required_skills` | text[] | 必要スキル。ユーザーのスキルと突き合わせる |
| `category` | text | 大分類。`work_kind` は細分類として残す |

`required_skills` は自由文字列ではなく、`lib/skills.ts` に定義したキーの集合に限定する。
自由入力にすると表記ゆれで一致しなくなり、フィルタもレコメンドも機能しなくなる。

### 3.3 表示項目の対応（v1 第3節）

| v1の表示項目 | 対応 |
|---|---|
| オファー名 | `title` |
| 報酬額 | `reward_points`（pt） |
| 所要時間 | `estimated_minutes`（**追加**） |
| 締切 | `ends_at` |
| カテゴリ | `category`（**追加**） |
| 難易度 | `difficulty`（**追加**） |
| 必要スキル | `required_skills`（**追加**） |

加えて、一覧には**残り募集数**（`max_completions_total` − 提出済み）と
**検収方法**（すぐ確定か、チェック待ちか）を出す。作業前に「いつ報酬が入るか」が
分からないのは、実際に人が離れる理由になる。

## 4. 画面と遷移

```
/work                一覧（フィルタ・並び替え）
  └ /work/[id]       詳細（説明・報酬・所要時間・必要スキル・検収方法・締切）
       └ 開始        提出フォーム（config.fields から生成）
            └ 送信   → 検収へ
/work/mine           自分の提出と状態
```

### 4.1 提出の状態遷移

```
提出 ──▶ pending（獲得予定）
           ├─ auto/none        ─▶ verified（確定・即時）
           ├─ review  運営承認 ─▶ verified
           │          運営却下 ─▶ rejected（理由つき）
           └─ quorum  賛成N   ─▶ verified
                      反対N   ─▶ rejected
```

ユーザー側の表示は「提出済み → チェック中（n/N）→ 確定」「やり直し（理由）」。
現行の `/tasks` は一覧内で完結しているため、詳細ページと `/work/mine` は新規。

## 5. 検索・フィルター（v1 第3節）

**絞り込み**: カテゴリ / 難易度 / 報酬額（下限） / 所要時間（上限） / 必要スキル /
締切（今日中・今週中） / 検収方法（すぐ確定のみ）

**並び替え**: 報酬が高い順 / 所要時間が短い順 / **時間あたりの報酬（pt÷分）が高い順** /
締切が近い順 / 新着順

「pt/分」はこの種のサービスでユーザーが実際に見る指標なので、既定の並び順の候補にする。

**一覧から除外するもの**（現行 `getActiveTasks` の方針を維持）: 停止中、期間外、
案件が稼働していない、募集上限に達した、自分が上限まで実施済み、クールダウン中。
押しても失敗するものを並べない。

---

## 6. 品質管理

### 6.1 既にあるもの

3つの検収モード（運営検収 / 相互チェック / 自動）。相互チェックは
自分の提出は不可・1人1票・規定数の反対で却下、をRPC側で担保している。

### 6.2 追加が必要なもの — ゴールドスタンダード設問

v1 第5節の「正答率」を出すには、**正解が既知の設問**を混ぜる以外に方法がない。
相互チェックだけでは「他人がOKを押した率」しか測れず、中身を見ずにOKを押す人がいると
その数字は汚染される。

- `tasks.config.gold` に、正解が分かっている設問とその答えを持つ
- 提出時に自動採点し、`task_completions.gold_score` に記録
- 閾値未満は自動却下（人手の検収に回さない）
- この採点結果だけを「正答率」の算出に使う

### 6.3 相互チェック自体の不正

中身を見ずにOKを押し続けるだけでチェック報酬が貯まる、という穴は現在も開いている。

- 却下された提出にOKを入れていた人のチェック報酬を戻す
- チェック内容の抜き取り監査
- 一定期間の不一致率が高い人をチェック側から外す

MVPでは1つ目（報酬の巻き戻し）だけ入れる。

## 7. ユーザー評価（v1 第5節）

### 7.1 算出する指標

| 指標 | 算出 |
|---|---|
| 完了数 | `verified` の提出数 |
| 承認率 | 承認 ÷ (承認 + 却下) |
| 品質スコア | 下記のベイズ平均 |
| 正答率 | ゴールドスタンダード設問の正解率（6.2） |
| 得意カテゴリ | カテゴリ別の承認率と件数 |
| 作業実績 | 直近30日の提出数・平均所要時間 |

### 7.2 品質スコア

件数が少ないうちに「1件承認＝100%」が出ると評価として使えないので、全体平均に寄せる。

```
品質スコア = (承認数 + m × 全体承認率) ÷ (提出総数 + m)     m = 10
```

`m` は「全体平均から離れるのに必要な件数」。10件程度でその人自身の実績が支配的になる。

### 7.3 用途

レコメンド（第8節）、発注者への提示（第9節）、将来的にはスキル別の単価差。
**予測市場の的中率との統合は本書の対象外**（v1 第5節の将来構想として保持）。

---

## 8. レコメンド（v1 第7節）

MVPはルールベース。AIによるマッチングは対象外。

**除外**（絶対に出さない）: 実施済み・上限到達・クールダウン中・必要スキル不足・
案件停止中

**並び順のスコア**

```
score = スキル一致度 × 0.4
      + そのカテゴリの実績 × 0.3
      + pt/分 × 0.2
      + 新着 × 0.1
```

実績のない新規ユーザーには、必要スキルなし・難易度 `easy` のオファーを優先して出す。
最初に見えるものが実行できないと、そこで離脱する。

## 9. 発注者機能（v1 第6節）

### 9.1 権限

`profiles.role` に `sponsor` を追加し、`profiles.sponsor_id` で発注者に紐付ける。
**自社の案件・オファー・提出しか見えない／触れない**ことをサーバー側で担保する。
既存のRPCが `service_role` 経由なので、RLSではなくアプリ層のガード
（`lib/adminGuard.ts` と同じ形）で統一する。

### 9.2 発注者ができること

| 操作 | 備考 |
|---|---|
| オファーの作成・停止 | 自社の案件配下のみ |
| 報酬・募集人数・締切・必要スキル・難易度・所要時間の設定 | |
| 品質基準の設定 | 検収方法、必要チェック数、ゴールドスタンダード設問 |
| 提出内容の閲覧 | 自社オファーのみ |
| 回答データのエクスポート | CSV / JSON |
| 進捗の確認 | 提出数・承認数・残り募集数 |

### 9.3 発注者ができないこと

- 単価・予算の自己変更（運営が設定する。勝手に下げられると作業済みの人が損をする）
- 他社のデータの閲覧
- ユーザーの個人情報の閲覧（表示するのはユーザー名と実績のみ）
- 検収の直接操作（品質基準は設定できるが、個々の承認・却下は運営と相互チェックが行う）

---

## 10. 通知（v1 第8節）

**トリガー**: 新着オファーがユーザーのスキルに一致 / 提出が承認された /
提出が却下された / 締切が近い未完了のオファー

**文面**: 単位はpt。実際に出せる額で書く。「3分・300円」のような、
成立しない単価を出さない（第12節）。

**送信手段**: Webプッシュ（Service Worker）。MVPではアプリ内の通知一覧のみとし、
プッシュ配信は次段階。

---

## 11. WORK / PREDICT の切り替え（v1 第9節）

同一アカウント・同一ポイント残高。下部ナビを2つの世界に分ける。

```
WORK      /work      オファー一覧・自分の提出・実績
PREDICT   /markets   マーケット・ニュース
共通      /mypage    残高・履歴・設定
```

WORKで得たポイントはそのままPREDICTで使える。これは換金性がないから成立する構成で、
第2.1節の決定と一体。

## 12. MVPスコープ

### 実装済み

オファーの実行・提出、3つの検収モード、相互チェック、案件と予算の管理、
採算表（円）、管理者によるオファー作成、検収キュー

### 今回作る

1. オファー属性の追加（所要時間・難易度・必要スキル・カテゴリ）
2. 一覧の検索・フィルター・並び替え
3. オファー詳細ページ、`/work/mine`
4. ユーザー実績（完了数・承認率・品質スコア・カテゴリ別）
5. ゴールドスタンダード設問と正答率
6. 発注者ポータル（ロール・アクセス制御・エクスポート）
7. ルールベースのレコメンド
8. WORK / PREDICT のナビ分割

### 作らない

出金・換金、AIによる自動マッチング、Webプッシュ配信、
予測市場の的中率とWORK実績の統合、スキル別の単価差

## 13. 未解決の論点

**単価の現実性** — v1 第8節の「3分・300円」は時給6,000円。発注者から受け取る額に
運営の取り分を乗せて成立する水準ではない。国内のマイクロワークの相場を踏まえると、
3分の作業なら数十pt規模が現実的。ここは最初の案件の実単価が決まってから確定する。

**労務性** — 継続的・指揮命令的な作業は労働契約の議論に入りうる。単発・自由参加・
時間の拘束なし、という建て付けを崩さない。利用規約 第4条に記載済み。

**個人情報** — 現地調査・写真提出を扱う場合、第三者が写り込む。取得の可否と
発注者への提供範囲をオファーの種類ごとに決める必要がある。

**多重アカウント** — 未対応のまま。実績と品質スコアを導入すると、
低評価アカウントを捨てて作り直す動機が生まれる。メール確認は前提条件になる。
